# Maintaining the mockups

Notes for whoever edits the mockups. What they are is in the [README](README.md), the rules every screen follows in [DESIGN.md](DESIGN.md), and what changed in each version in [CHANGELOG.md](CHANGELOG.md).

## Running them

- There is no build step: open any `.dc.html` file in a browser, or serve the folder (`python3 -m http.server 8767`) and open `http://localhost:8767/`.
- The published site, https://aurora-wellcome.github.io/clinician-dashboard-prototype/, updates when `main` is pushed. `index.html` is its landing page.
- **Open tabs pick up new builds** (from October 26). Browsers may reuse a page for 10 minutes, so opening the link again already gets the latest version, but a tab left open never checks. So `notes.js` checks every 5 minutes while a page is in view, and whenever the reviewer comes back to it.
  - **How:** GitHub Pages stamps every file with the time of the deploy (Last-Modified), so the check compares the page's own stamp (`document.lastModified`) with a fresh HEAD request for the page. Any deploy counts, even one that changes only the docs.
  - **When the reviewer comes back** to a tab with a newer build, the page reloads itself. The address keeps the page, patient and settings. If they're typing, or partway through something a reload would lose (a note, reply, edit or answer, the handout's topics or wording, the site settings, Your settings or a patient's alerts), a bar offers Reload instead, as it does while they stay on the page.
  - **Before reloading,** it fetches the page's own scripts fresh into the browser's cache, so the new page can't run with old scripts. It also saves the build it reloaded for (`aurora-reload-target` in sessionStorage), so a reload that brings back the old page shows the bar rather than looping.
  - **Testing:** pages opened from disk aren't checked. A local server works: `python3 -m http.server` sends Last-Modified from each file's modification time, so touching a file stands in for a deploy.
  - Tabs opened before this change need one reload by hand.
- **Scripts carry a stamp** (from November 6): every page names its scripts with a hash of their contents, as `./notes.js?v=5eaf0e5c5f`, and `index.html` names `bear.js`, `moon.js`, `cabin.js` and `cabin-music.js`, which it loads later, the same way. A changed script gets a new address, so a reload, or a visit within the 10 minutes GitHub Pages lets browsers keep files, fetches it rather than reusing the old copy, and a page never runs with a script from another build: nobody needs a hard refresh. The check above still covers tabs left open.
  - **After changing a `.js` file,** run `python3 tools/stamp.py`, which updates the stamps in every page, `archive/` too, and commit those pages with the script. `python3 tools/stamp.py --check` only reports.
  - **A pre-commit hook,** `tools/hooks/pre-commit`, can refuse a commit whose staged pages don't match the staged scripts (`python3 tools/stamp.py --staged`). It's off until turned on, once per clone: `git config core.hooksPath tools/hooks`.
  - Images and the arcade font aren't stamped: they rarely change, and a changed one shows within 10 minutes.
- `support.js` is the shared runtime the pages load. Keep it alongside the HTML files.

## Deep links

A link can open a specific page and settings:
- `#view=list&dates=1` shows visit dates, which are off by default (the list is then grouped by status, by last name). With them on, `&order=visit` (by next visit, the default) or `&order=status`. By next visit, `&flagged=day` (the default) lists safety-flagged patients under their visit day, `&flagged=pinned` only in a group at the top, and `&flagged=both` in both places (v3).
- `#view=list&sort=name` or `&sort=sev` (v3: the patients list sorted by last name or by severity, safety flags first; add `&rev=1` to reverse)
- `#view=patient&p=delgado`; `&lead=ai` puts the AI estimate's tile first (v3)
- `#view=handout&p=delgado`; `#view=handout&p=fernandez&lang=en` (v3: the handout in English for a patient whose check-ins are in Spanish); `&ho=simple` for the simple handout (v3); `&hom=ai` or `&hom=both` for the full handout's chart on the AI estimate, or both (v3)
- `#view=checkin&p=delgado&d=2026-08-10` (v3: one check-in; without `&d=`, the patient's example or latest check-in)
- `#view=site` (v3: the site PI page), `#view=settings` (v3: site settings) `#view=account` (v3: Your settings) and `#view=welcome` (v3: the first page after signing in); `#view=list&empty=1` shows the caseload before the first patient
- `&line=checkins` (the default), `pages`, `clinicians` or `none` sets the greeting's last line (Refined look).
- Add `&clock=24` for 24-hour times, `&drivers=1` to open the drivers panel (v3), `&look=current` for v3's Original look, and `&hero=0` to hide the greeting band.
- Older links' `&style=`, `&text=` and `&icons=` settings are ignored: those choices are settled.

Patient ids: `osei`, `whitfield`, `delgado`, `fernandez`, `nguyen`, `mensah`, `santoso`, `kaur`, `brooks`, `ortiz`, and in v3 also `haddad` and `novak`.

## Review notes

Reviewers can pin notes to any part of the v2 and v3 pages and the landing page. The notes code is in `notes.js`. The landing page loads it with `data-page="landing"`, which gives the landing page its own list of parts, with no patient or settings. A note can be marked as an idea, problem, question or like, and others can reply, +1 or resolve it.
- **Who sees what:** reviewers see others' notes on a page once they have added one there, so the first notes don't steer the rest. The facilitator link shows every note.
  - **Seeing them first** (from October 27): the panel's line about hidden notes has a "Show them now" button, and a line to hide them again. The page knows a reviewer only by their browser (an anonymous Firebase sign-in), so on a second computer or browser their earlier notes don't count and others' notes stay hidden. The choice is kept in that browser (`aurora-notes-show-others` in localStorage).
  - Answers to the questions keep their own rule: others' answers to a question appear once you've given yours, since tallies seen first would sway the group's choices more than notes do.
- **Access:** notes are shared through a Firebase project (Firestore, with anonymous sign-in). The site is public, so access comes from the review link, which carries a private board id: `AURORA%20Dashboard%20v3.dc.html?board=<board id>`. Add `&facilitator=1` for the facilitator link. The link can open a mockup page or the landing page (`https://aurora-wellcome.github.io/clinician-dashboard-prototype/?board=<board id>`); the browser then remembers the board for every page. Either way, the first page a reviewer opens from the link shows the Notes panel, so they find it.
- **Entering the code by hand:** two places open a dialog for the access code (or a whole review link): the landing page's Leave notes step, and the Notes panel whenever notes aren't shared. The code is saved in the browser (`aurora-notes-board` in localStorage), so every page, the mockups and the landing page, then shares notes. The landing page can also remove it. If the browser already holds notes saved only there, the dialog offers to copy them to the shared board; the copy happens when the page next connects (`aurora-notes-carry`). A wrong code gets a plain-language message, and until a code works, new notes stay in the browser.
- **Meteor showers:** the shooting star game's `SHOWERS` list in `index.html` holds each shower's entry speed and peak dates, from the American Meteor Society's 2026-27 calendar (amsmeteors.org/calendar). Peaks can move by a day or so from year to year, so check the dates if the page is still in use after August 2027. The moon game names its meteor shower from the same list, which `index.html` hands it.
- **Sites:** the list reviewers choose from is `SITES` in `notes.js` (trial sites from the proposal, then partner organizations). Scores store the full name, and the high score table shortens long ones through `SHORT` in `index.html`, using only letters the pixel font has. When renaming a site, keep the old name in `SHORT`, since saved notes and scores keep the name they were saved with. The notes' rules already accept the field; the rules for scores take it from the November 5 version of `firestore.rules`, and until those are published, a score saves without its site.
- **High scores:** the shooting star game's shared table is in the same Firebase project, at `boards/<board id>/scores`, read through `window.auroraLeaderboard` from `notes.js`. Each entry holds the initials, the points, the time and the anonymous uid. Scores can only be added; to remove one, delete it in the Firebase console (Firestore > `boards` > the board id > `scores`, or `bearScores`, `moonScores` or `cabinScores` for the other games). The scores' rules are the second block in `firestore.rules`. Until they are in the console, the game quietly keeps scores in the browser only. The bear game's table is at `boards/<board id>/bearScores`, read through `window.auroraLeaderboard.bear`, and each entry also holds the animal played. Its rules are the third block, which lists the animals it accepts. The moon game's table is at `boards/<board id>/moonScores`, read through `window.auroraLeaderboard.moon`, and each entry also holds how far the run got (`reached`: a stage's name, `Partial eclipse` or `Total eclipse`), which the table shows as Reached. Its rules are the fourth block, which lists the values `reached` can take, so renaming a stage means changing them too. The cabin game's table is at `boards/<board id>/cabinScores`, read through `window.auroraLeaderboard.cabin`, and each entry also holds how far the run got (`reached`: `Spring`, or the month the fire went out, `November` to `March`), shown as Reached. Its rules are the fifth block, published on November 7, which lists those values too. Paste `firestore.rules` into the console (Firestore > Rules, with the board id in place of `BOARD_ID`) before people play the moon game: until then its table can't be read or written, and the game quietly skips it (`window.auroraArcade.gameEnded` returns false), so a run ends with its result line and the best score stays in the browser.
- **The board id is not in this repo:** `firestore.rules` is the template for the project's rules, with the id left out. The Firebase web config in `notes.js` is public by design; the rules are what protect the notes.
- **Without the link,** notes are saved in that browser only.
- **What a note records:** the version, page, patient, part of the page, and the settings in use (section style, text size, icons, visit dates, caseload order and sorting, time format, look); by next visit, where safety-flagged patients appear; on the check-in page, which check-in; on the v3 handout, its language and style. A note’s Show link, from another page, opens its page with those settings. It also records the site build the page was loaded from (`build.json`, which GitHub Pages fills in with the commit and build time on each deploy), so a note written in a tab opened before an update is matched to what the reviewer saw. **Download notes (CSV)** exports them.
- **Pins:** with the panel open, every note listed under This page has a pin on its part of the page. Every patient's page, handout and check-in has the same parts, so This page lists the notes from all of them, and a note written on one patient's page is pinned to the same part on the others; the pin's label for screen readers says whose page it was written on. Clicking a note in the panel finds its pin or, for a note written on another patient's page or check-in, opens that page. A note whose part isn't on screen (the drivers panel while it's closed, the Model Facts dialog) has a Show link instead. When a part notes can be pinned to is renamed (a tile, a group, a section heading), add the old name to `RENAMED` in `notes.js`, so notes on it keep their pins.
  - **Moving pins** (from November 1): a pin can be dragged out of the way of what it covers, or moved with the arrow keys once it has focus (Shift for longer steps). A dashed line leads back to a dot on the spot it marks. Moves are kept in that browser (`aurora-notes-moved` in localStorage), as offsets from the spot, so a pin follows its part when the page reflows. Others still see the pin where its writer put it; the Firestore rules wouldn't let a reviewer move others' notes anyway. When pins on a page are moved, the panel says so and offers to put them back.
- Notes are review scaffolding, like the review strip: they don't print, and the note form asks reviewers to leave out patient information.
- **Questions** (v3): the panel's Questions tab holds questions for the working group, listed in `QUESTIONS` in `notes.js`, each with a "Show me" link to the page and settings it is about. An answer is saved as a note of kind `answer`, with the question (`q`), the choice and an optional comment, so the Firestore rules need no change. Saving again updates the reviewer's answer. Answers aren't pinned or listed with the notes. Others' answers to a question appear once a reviewer has answered it, and the facilitator link shows them all. The panel's CSV export includes them, with question and choice columns.

## Screenshots and images

- `design/landing/`: the screenshots `index.html` shows, one per version: the caseload in a 1200 × 750 window at 4/3 scale (1600 × 1000 pixels), without the review strip or the Notes button (hide `.review` and the notes' `an-` classes with injected CSS). Regenerate them when a version's caseload or patient page changes.
- `design/landing/banner_gen.py` draws the landing page's aurora banner as layers, which the page animates slowly. To regenerate it:
  1. Run `python3 design/landing/banner_gen.py banner.html plane.css`.
  2. Paste `banner.html` over the banner in `index.html`.
  3. Paste `plane.css` over the `bn-plane-a` and `bn-plane-b` keyframes (the far-off plane's arcing paths).

  The script also writes `design/landing/forest.svg`, the forest's silhouette alone, which masks the starlight the page adds to the treetops. The banner HTML includes `.bn-scene`, which holds the cabin's smoke and firelight, and the puff and sparks when someone clicks it, at positions computed from the drawing. `.bn-scene` covers the same box as the forest layer, so its `cqw` units are the drawing's (1cqw is 16 units).

  The script also places the Big Dipper and the North Star (from the stars' coordinates; `DIPPER_TURN`, `POINTER_GAP` and `DIPPER_BOX` set its turn, the North Star's spacing and its place) and the moon (`MOON`), and leaves out random stars that would crowd the figure. The page hides the stars near the moon, wherever a narrow or wide banner moves it. The page's script draws the moon for the date and sets the time of day. To see another date and time, add `?at=` to the address, for example `index.html?at=2026-11-24T22:30` (a full moon, near midnight).
- `design/landing/moon_gen.py` makes the moon's textures, `moon_albedo.webp` and `moon_relief.webp`, from NASA's [CGI Moon Kit](https://svs.gsfc.nasa.gov/4720/). Download `lroc_color_poles_4k.tif` and `ldem_16.tif` (about 80 MB, not kept here), then run `python design/landing/moon_gen.py lroc_color_poles_4k.tif ldem_16.tif` with numpy and Pillow installed, and regenerate the banner as above. `banner_gen.py` puts the textures in the banner as data URIs, so the page can light them in a canvas even when it is opened from disk. The lighting is `lightMoon` in `index.html`. `drawMoon` draws tonight's moon with it; below `NEW_MOON_LIT` (3% lit) it adds a faint outline and gives the moon the class `new` in place of `on`, so the moon game and the pointer's lighting treat it as there, while the bear game and the high score table's picture of the moon, which read `on`, don't.
- `design/landing/arcade.woff2`: the pixel font of the high score table and the game's credits, 46 characters of [Press Start 2P](https://fonts.google.com/specimen/Press+Start+2P) by CodeMan38, subset by Google Fonts. Its license (SIL Open Font License) is `design/landing/arcade-font-OFL.txt`.
- `design/screenshots/`: dated before/after screenshots for each redesign round.
- Content audits quote the planning meetings, so they stay out of this public repo (`.gitignore`).
- `design/type-check.html` lists the words at each rendered text size. Serve the repo first, then open `http://localhost:8767/design/type-check.html`.

## Other files

- `notes.js`: review notes, loaded by v2, v3 and the landing page. `firestore.rules`: the template for its Firebase access rules. `build.json`: the site build, filled in on deploy.
- `tools/stamp.py`: stamps the pages' references to the scripts with a hash of each (see Running them), and `tools/hooks/pre-commit`, the hook that can check them before each commit.
- `bear.js`: the bear game, which `index.html` loads (`loadBear`) only when someone starts it, or when the browser has unlocked an animal, to draw its stars. Unlocked animals are a comma-separated list in localStorage (`aurora-animals`). To try the fox without earning it, run `localStorage.setItem('aurora-animals', 'fox')` in the browser's console and reload, or `'fox,crab'` for the crab too; remove the key to lock them again. The animals brought home are `aurora-homes`, and the first time it holds all three, the grand finale plays: to see it again, run `localStorage.setItem('aurora-homes', 'bear,fox')` and bring the crab home, or play it on demand on the landing page with the Konami code (↑ ↑ ↓ ↓ ← → ← → B A) or three quick clicks on the North Star. Each animal's best score is `aurora-bear-best`, `aurora-fox-best` or `aurora-crab-best`, and the sound setting, `aurora-banner-sound`, is shared with the shooting star game. The music is in `bear.js`: `TUNE` for the bear, `FOX_TUNE` for the fox, `CRAB_TUNE` for the crab and `SPRING_PHRASE` for the finale (by sixteenth note), bar by bar, each bar's chord root and its melody, as MIDI notes and lengths in eighth notes, with `'yip'` after a fox's yip. `SONGS` sets each one's tempo and how it's played, and `MUSIC_LEVEL` its loudness under the effects. The shooting star game's is `SKY_TUNE` in `index.html`, which also says whether each bar's chord is major, with `SKY_BPM` and `SKY_LEVEL`. The stages are `STAGES`: each star's name, how often stars and bees come, and its card's line; `POINTS` is how many stars each stage needs, one for each point of its big star. The `_FROM` constants after it say which stage brings honey, the airliner, the moon and swooping bees, and `NIGHT_SECONDS` sets the night's length; the comment above it gives the bot timings it was set from. `GROW_EACH`, `GROW_BERRIES` and `GROW_STING` set how much each berry makes the animal grow, after how many it stops and how many berries' worth a sting takes back; the comment above them says what has to stay its usual size and why, and `SHED_SECONDS` is how long the crab's old shell stays. The `LEDGE_` constants set where the bridges can move to between stages and how their stars fly there; `moveLedges` applies them, with its comment giving the fallbacks for narrow banners. An animal's `start` in `ANIMALS` is the size it starts each run at, as a share of its sizes there: 0.85 for the bear, and 1 for the fox and the crab, which don't give one.
- `moon.js`: the moon game, which `index.html` loads (`loadMoon`) only when someone starts it, from a click on the moon or Play again in its high scores, as `./moon.js?v=<stamp>`; `tools/stamp.py` stamps it with the other scripts (see Running them). The page hands it the moon's maps, which it copies to mark with craters, `lightMoon` to light them, `sunAt`, and the meteor showers with the date. The best score is `aurora-moon-best` in localStorage, the power-ups whose card has been shown are `aurora-moon-powers` (remove the key to see the cards again), and the sound setting, `aurora-banner-sound`, is shared with the other games. `?moonflow=0.7` on the landing page's address runs everything that streams past at 70% of its speed (`FLOW`, from 0.3 to 1.5), for trying the game on people. The constants at the top set the game, with comments: `STAGES` (each stage's phase, length, card, how often rocks come and what it brings), the pace (`SPEED` and `PACE_GAIN`, with `LOOK` and `FEWEST` for narrow banners), the halo (`HALO_POOL = true` puts back the first rule, where a rock reaching the moon took halo stars in place of a life), the eclipse (`TOTAL`, `TOTAL_MAX`, `ECLIPSE_SECONDS`) and `POWERS`. The music is `WALTZ`, bar by bar, each bar's chord and its melody as MIDI notes and lengths in eighth notes, with a third item where the melody changes in the minor; `WALTZ_BPM` and `WALTZ_TEMPO` set its pace in each stage, `DANUBE` and `DANUBE_BPM` are The Blue Danube, and `MUSIC_LEVEL` keeps both under the effects. The credits after a total eclipse name the next real one, August 2, 2027, so change them if the page is still in use then. Balancing the game with bots at 1440 px and on a phone, as for the other games, is still to come.
- `cabin.js`: the cabin game, which `index.html` loads (`loadCabin`) only when someone starts it, from a click on the cabin outside a game or Play again in its high scores, as `./cabin.js?v=<stamp>`. The page hands it its own stoke of the cabin's fire, the aurora's surge for the thaw, and the address of `cabin-music.js`, so that `tools/stamp.py` stamps that too. The best score is `aurora-cabin-best` in localStorage, and the sound setting, `aurora-banner-sound`, is shared with the other games. The constants at the top set the game, with comments: the ridge and its rings (`PATH`, `RIGHT_PATH`, `RINGS`, `RING_GAP` and the rest), wood (`START_WOOD`, `CORD`, `NEXT_WOOD`), `BUILD` (each building's costs, reach and melting by level), `HOST` (each kind in the army: its health, size, speed, points, wood and the lives it costs), `WRAITH`, Old Man Winter (`KING_AT`, `RAISE`, `RAISE_EVERY`, `KING_STOKE`), `MONTHS` (each month's length, how often ranks come and what they hold, its card and its lines), the stoke and its reminder (`STOKE_EVERY`, `NUDGE_IDLE` and the rest), and star lanterns (`STAR_EVERY`, `STARS`). They were balanced with bots playing whole winters at 768, 1440 and 1920 px (DESIGN.md), so a change to them is worth checking the same way. The music: `WINTER` sets each of Winter's passages' tempo and which voice plays each part, how loud; `VOICES` how each voice sounds; `SPRING` is the bear game's Spring, for the thaw; and `MUSIC_LEVEL` keeps it all under the effects.

## Runtime quirks

- **Tables:** in a page's template, write tables with the runtime's raw tags (`sc-raw-table`, `sc-raw-thead`, `sc-raw-tbody`, `sc-raw-tr`, `sc-raw-th`, `sc-raw-td`); they render as ordinary tables. With plain `<table>` tags, the browser moves `<sc-for>` loops out of the table. The runtime repairs that only when the page is served, so a page opened straight from disk shows an empty table.
- **Values in SVG text:** the runtime wraps each `{{ }}` value in an HTML `<span>`, which SVG doesn't draw, so a value inside `<text>` must go through `T()` (a React fragment), as the charts' dates and the simple handout's scores do.
- **Boolean attributes:** give `checked`, `disabled` and the like a value, as in `checked="{{ o.on }}"`. A bare `checked` or `disabled` reaches React as an empty string, which it reads as false, so the box shows unchecked or enabled (Your settings' always-on Email box did).
- **Chart labels** are SVG text, which can't hold HTML such as an ⓘ button. The label on the baseline + 6 line ("Worse than baseline") is drawn in HTML over the chart instead, sized with the chart (see `.thr-tag`).
